# 기존 웹 서버와 MCP 함께 실행하기

**Python 3.9.13을 그대로 유지**하면서 기존 `main:app`의 **동일 포트 `/mcp`** 로 Streamable HTTP MCP를 제공합니다. 별도 서버·Docker·Node.js·최신 MCP SDK가 필요하지 않습니다. 서버 통신부는 Python 3.9 호환 코드로 구현했습니다.

## 1. 실행 환경 설치

다음은 Linux 배포 서버에서 현재 Gunicorn을 실행하는 가상환경에 적용합니다.

```bash
python --version
python -m pip install -r requirements-web-mcp.txt
```

**Python 3.9.13과 기존 가상환경을 그대로 사용합니다.** 최신 파일을 서버에 올린 뒤 위 설치 명령을 실행하세요. 이 파일은 기존 웹 패키지에 `httpx==0.28.1`, `jsonschema==4.23.0`만 추가하며 최신 `mcp` SDK를 설치하지 않습니다.

이전에 안내한 `requirements-mcp.txt`는 선택적인 Python 3.11 이상 로컬 stdio 도구용입니다. **현재 3.9 서버에서는 설치하지 마세요.** 기존 `requirements-web-mcp.txt`도 반드시 이번 수정본으로 교체해야 합니다.

## 2. 허용 주소 설정

서버 `.env`에 다음을 추가합니다. 아래 도메인은 예시이며 실제 주소로 바꿔야 합니다.

```dotenv
BG_MCP_HTTP=1
BG_MCP_ALLOWED_HOSTS=example.com,127.0.0.1:8080,localhost:8080
BG_MCP_ALLOWED_ORIGINS=https://example.com
```

- `BG_MCP_HTTP=1`: 필요한 패키지(`httpx`, `jsonschema`)가 없으면 시작 오류로 알립니다. 기본 `auto`는 패키지가 있으면 함께 실행하고, 없으면 기존 웹을 유지하되 `/mcp`에서 503을 반환합니다. `0`은 HTTP MCP를 끕니다. 앞서 안전을 위해 0으로 바꿨다면 설치 후 **1로 되돌려야 합니다.**
- 기본 허용 호스트는 localhost·127.0.0.1·IPv6 루프백뿐입니다. 실제 접속 도메인을 누락하면 MCP 요청에 421을 반환합니다.
- 호스트는 요청의 Host 값과 일치해야 합니다. 포트가 붙는 주소는 포트도 포함하세요. `0.0.0.0`은 바인딩 주소이지 접속 호스트가 아닙니다.
- 외부에서는 HTTPS 역방향 프록시를 사용하세요. 8080 포트를 평문으로 인터넷에 공개하여 인증 토큰을 보내지 마세요.
- 프록시는 기존 Host와 Authorization 헤더를 보존해야 합니다. 허용 주소에 전체 별표를 쓰지 마세요.

## 3. 기존 명령으로 시작

현재 사용하시는 명령을 그대로 사용합니다.

```bash
gunicorn main:app -w 2 -k uvicorn.workers.UvicornWorker -b 0.0.0.0:8080 --daemon --access-logfile logs/gunicorn-access.log --error-logfile logs/gunicorn-error.log --capture-output --log-level info --pid logs/gunicorn.pid
```

이미 데몬이 실행 중이라면 기존 배포 절차로 종료한 뒤 재시작하세요. `logs` 디렉터리가 존재하고 실행 계정이 쓸 수 있어야 합니다. 운영 서버의 Python 버전 확인·패키지 설치·재시작은 별도 배포 작업이며 이번 로컬 코드 변경만으로 운영 서버에 반영되지 않습니다.

## 4. MCP 클라이언트 연결

- 전송 방식: **Streamable HTTP**
- 주소: `https://실제도메인/mcp`
- 인증 헤더: `Authorization: Bearer <본인 MCP 전용 토큰>`

웹사이트에 로그인한 뒤 MCP 연결 화면에서 본인 전용 토큰을 발급합니다. 원문은 발급 직후 한 번만 표시되며 계정별 활성 토큰 1개, 유효기간 30일입니다. 재발급·폐기·비밀번호 변경·계정 삭제·만료 후에는 이전 토큰을 사용할 수 없습니다. 역할 변경은 다음 요청부터 적용됩니다. 토큰을 채팅·공유 설정·명령 기록에 노출하지 마세요.

호환성을 위해 기존 웹 로그인 JWT도 `/mcp`에서 계속 수용합니다. 새 화면은 전용 토큰만 안내합니다. 기존 `mcp_login.py`와 로컬 stdio는 웹 JWT를 사용하는 별도 호환 경로입니다. 전용 토큰으로 직접 `/api/`를 호출할 수 없습니다.

**사용자 지정 인증 헤더를 지원하는 MCP 클라이언트가 필요합니다.** 기존 사이트 Bearer 인증을 사용하며 OAuth 자동 로그인·자동 클라이언트 등록 서버를 추가한 것은 아닙니다. 브라우저의 로그인 쿠키만으로는 MCP에 접근할 수 없습니다.

## 동작 방식

- 세션 비저장 방식이므로 `-w 2`에서 요청이 다른 워커로 넘어가도 됩니다. 세션 고정·Redis·별도 포트가 필요하지 않습니다.
- 별도 MCP 전송 관리자나 백그라운드 프로세스를 만들지 않습니다. 기존 웹 시작 시 전용 토큰 테이블만 추가 생성하며 종료 생명주기는 변경하지 않습니다.
- MCP 2026-07-28의 `server/discover`, `tools/list`, `tools/call`과 필수 메타정보·헤더 검증을 구현합니다. 2025-11-25의 `initialize`, 초기화 알림, `ping`도 호환합니다. 응답은 단일 JSON이며 구독·SSE 알림·리소스·프롬프트·샘플링·비동기 작업을 광고하지 않습니다.
- 매 HTTP 요청의 토큰을 확인하고 도구 호출도 기존 API를 통해 권한을 다시 검사합니다. 관리자 토큰을 공용 환경변수로 공유하지 않습니다.
- 계정 삭제·역할 변경·토큰 만료를 다시 확인하며 동시 사용자 요청의 토큰을 서로 섞지 않습니다.
- 내부 조회는 같은 워커에서 ASGI로 호출합니다. 자기 Gunicorn 포트로 재접속하지 않으므로 포트와 워커 개수에 독립적입니다.
- 기존 66개 읽기 전용 도구와 개인정보·쓰기 차단 경계를 유지합니다. stdio 실행도 계속 사용할 수 있습니다.

## 간단한 상태 확인

`/mcp`에 토큰 없이 요청했을 때 **401**이면 인증 경계가 동작하는 것입니다. **503**은 필요한 패키지 미설치, **421**은 허용 호스트 설정 문제입니다. MCP는 JSON-RPC 프로토콜이므로 단순 브라우저 GET으로 도구 목록을 확인할 수는 없습니다.

테스트:

```bash
# 실제 Python 3.9 서버에서 실행 가능, 최신 SDK 불필요
python -m unittest discover -s tests -p 'test_mcp_*.py'

# 별도 Python 3.11+ 개발 환경에서만 공식 클라이언트와의 상호운용 검사
# python -m unittest discover -s tests_mcp -p 'test_*.py'
```

Windows 검증 환경에서는 Gunicorn 자체 실행을 검증할 수 없습니다. 대신 동일 앱 두 인스턴스 사이에서 초기화와 다음 요청을 나누어 세션 비의존성을 검증하며 공식 MCP 클라이언트로 최신·이전 규격을 확인합니다.

## 기존 전송 구현 당시 검증 결과

아래 수치는 전용 토큰 도입 전의 검증 이력입니다. 전용 토큰 검증은 `tests/test_mcp_tokens.py`를 포함한 현재 테스트로 별도 실행해야 합니다.

- 공식 Windows 임베디드 **Python 3.9.13**에서 최신 MCP SDK 미설치를 확인하고 **전체 백엔드 테스트 349개 통과**. 별도 3.9.24 환경에서 필요한 패키지 설치도 성공.
- 공식 SDK 2.3.0 클라이언트를 사용하는 별도 3.11 환경에서 **MCP 테스트 17개 통과**. 이 중 교차 프로세스 검사는 실제 3.9.13 서버를 localhost에 기동하여 2026-07-28/2025-11-25 접속·66개 도구 목록·조회 성공을 확인함.
- 단순 구문 검사가 아니라 3.9.13의 실제 실행 결과이며 인증 격리·권한·읽기 전용 SQL·메타정보·헤더·오류 응답·기존 웹 기능을 포함함.
- [blocked] Windows 도구 환경의 개발 데몬은 셸 종료 후 지속 실행을 확인하지 못함. Linux 운영 Gunicorn 배포·실제 프로세스 지속 실행·HTTPS 접속은 배포 서버에서 확인해야 함. 테스트 앱 성공을 운영 배포 완료로 간주하지 않음.

## 전용 토큰 관리 API와 인증 경계

관리 API는 일반 선생님을 포함해 웹 로그인 사용자 본인만 사용할 수 있습니다. 응답에 `Cache-Control: no-store`를 적용합니다.

- `GET /api/user/mcp-token`: `enabled`, `active`, `created_at`, `expires_at` 반환. 시각은 UTC ISO 형식이며 발급 내역이 없으면 null입니다.
- `POST /api/user/mcp-token`: `{"confirmation":"MCP 토큰 발급"}`. 같은 상태 정보와 원문 `token`을 한 번 반환합니다. 비활성 서버에서는 503입니다.
- `DELETE /api/user/mcp-token`: `{"confirmation":"MCP 토큰 폐기"}`. 폐기 후 `active:false`, 시각 null을 반환합니다. MCP가 비활성이어도 폐기는 가능합니다.

`bgmcp_` 접두사의 256비트 난수 토큰은 DB에 SHA-256 해시로만 저장됩니다. 계정 번호와 사용자명 및 비밀번호 지문에 귀속되며 발급·폐기와 민감정보 없는 감사 이력을 같은 트랜잭션에 저장합니다. 감사 실패 시 변경도 취소합니다.

전용 토큰은 외부 `/api/` 인증에서 거부됩니다. `/mcp`의 고정 조회 도구 내부 ASGI 호출에만 HTTP 헤더로 위조할 수 없는 객체 표식을 부여하고 기존 API가 현재 권한을 다시 검사합니다. 읽기 전용 헤더는 인증 표식이 아닙니다. 관리 API는 도구 카탈로그와 OpenAPI에서 제외하며 66개 도구를 유지합니다. DB를 공유하는 여러 워커에서도 재발급·폐기 상태를 요청마다 확인합니다.

## 전용 토큰 도입 후 검증

- Windows의 실제 Python **3.9.13**에서 최종 전체 백엔드 **355개 통과**. 전용 토큰 발급·재발급·폐기·만료·현재 권한·비밀번호 변경 후 원복·계정 삭제·외부 API 차단·감사 실패 롤백 및 캐시 방지를 포함합니다.
- 공식 SDK 환경의 **17개 모두 통과**. 별도 Python 3.9.13 프로세스와 최신·이전 규격으로 통신하는 검사도 포함하며 건너뛴 검사는 없습니다.
- 테스트는 격리된 임시 DB 또는 DB 접근 차단 모형을 사용합니다. 운영 배포·운영 HTTPS 접속 완료를 의미하지 않습니다.
